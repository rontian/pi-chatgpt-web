# Workflow Protocol

## Purpose

The workflow protocol is **not** the ChatGPT Web private transport protocol. It is our own stable contract used between ChatGPT-generated intermediate text and `pi-chatgpt-web` workflow orchestration.

## Envelope

```text
<pi-chatgpt>
{"status":"need_context","requests":[]}
</pi-chatgpt>
```

Terminal:

```text
<pi-chatgpt>
{"status":"final"}
</pi-chatgpt>

FINAL CONTENT HERE
```

Error:

```text
<pi-chatgpt>
{"status":"error","message":"..."}
</pi-chatgpt>
```

## Parsing policy

1. deterministic parser first;
2. validate allowed status and shape;
3. malformed envelope is never executed as a context request;
4. optional helper model may classify/repair only under an explicit fallback policy;
5. workflow turn/size budgets always win over model requests.

## Context request model

The exact request catalog is deferred to the Prompt Workflow phase. Likely request classes include session-message ranges, already-known project metadata, and explicitly permitted local project reads. This protocol must not silently evolve into unrestricted local tool execution.

## Separation from Product Observations

Product observations (web search, GitHub app activity, citations, etc.) are data emitted by the ChatGPT product runtime. Workflow envelopes are instructions generated by our workflow prompt. They are separate channels and must remain separate in code.
